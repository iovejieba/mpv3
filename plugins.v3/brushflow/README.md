# 站点刷流 9.4

BrushFlow 9.4 在 9.3 的基础上落地 H&R 做种窗口合同（红区判定 + 删除前 re-announce）、
标定缓冲收敛下限，并修复收编解析器的实机 bug；其余行为与 9.3 一致。面向日常 NAS 用户维护”一套嵌套配置、一条决策链、一个操作入口”。首页健康卡直接回答任务是否正常、插件下一步会做什么，以及是否需要用户处理。

## 核心行为

- 每个任务独立管理站点、下载器、容量、带宽、筛选、下载健康和删种安全；全局容量只阻止继续新增，不跨任务抢占或删种。
- 选种先执行重复、跨站未完成、H&R、促销、明确体积、发布时间和文本硬过滤，再使用本地 30 天收益学习评分。
- Tracker 人数未知时保持中性；可信需求需要最近 3 次检查至少出现 2 次。
- 自动删种永久保护未完成、H&R、未到站点最低保种、排除标签、真实上传、有效活动连接和可信下载需求。
- 默认容量达到任务上限 90% 开始清理，降到 85% 停止；每轮和每天同时受数量、容量百分比和可选 GB 上限约束。
- 新启用或从旧版迁移的自动删种先进入 48 小时安全观察，只记录计划、不调用下载器；误判率超标或出现硬安全违规会自动延长。
- 正常低价值淘汰先写完整审计，再删除下载器任务及数据；Tracker 明确拒绝的无效任务只移除任务、保留数据。
- 未完成下载连续 3 次且跨度不少于 30 分钟无进度时，自动重新汇报 Tracker 并恢复一次；再次持续异常则暂停。连续低速也使用”修复一次→仍异常则暂停”，永不自动删除未完成数据。

## 站点 H&R 策略层（9.2 新增）

ExoticaZ 等全站 H&R 站点的每个种子都带 H&R 义务，9.1 的硬保护会让它们永远无法自动删除。
9.2 引入按站点 domain 注册的策略层：

- **豁免判定**（与站点官方规则对齐，只多保不早放）：该种子做种时长达到站点体积公式要求
  （ExoticaZ：`72+2x 小时，x<50GB；100·ln(x)−219.2023，x≥50GB`），**或**该种子
  上传量/体积达到豁免线；任一达标即解除保护，进入正常删种评估。
- **豁免线站点级配置**：内置默认 1.0（官方规则 0.9 + qB 本地统计与站点记账偏差的缓冲）；
  可在插件数据 `site_hr_policies` 按域名覆盖——0 表示关闭分享率通道（只看做种时长），
  低于官方规则 0.9 的配置会被拒绝。所有引用该站点的任务共用一个值。
- **选种侧联动**：存在策略的站点不再按”存在 H&R”一票否决候选（否则全站 HR 站永远选不到种）；
  删种侧保护由公式兜底。
- **fail-closed**：体积、做种时长或上传量数据缺失时一律维持保护；未完成/卡种永不自动删。
- **策略详情**：工作台”策略详情（专业信息）”展示每个种子的公式要求小时、已做种小时、
  豁免线与当前豁免状态；开启分享率控制的任务同时展示站点当前分享率与目标——
  MP 无该站点用户数据时，插件会在刷流前探活登录页（30 分钟缓存，失败静默降级），
  HTTP 401/403 会提示可能被 Cloudflare 拦截、需人工过盾。

## 站点 H&R 账本镜像层（9.3 新增）

ExoticaZ 的 H&R 判定存在客户端无法消除的口径差：做种要求必须在**下载完成后 96 小时内**
达成（锚点是完成时刻，离线消耗窗口但不计做种时长），服务器做种时长只在 announce 时入账
（两次 announce 之间倒计时冻结）。只按客户端统计判定会提前放行——实测漂移约 6 小时。
9.3 引入账本镜像，形成三层结构：

| 层 | 数据 | 作用 |
| --- | --- | --- |
| 基线闸门 | 公式(体积) + 客户端做种时长 + **标定缓冲**（起步 6h，EWMA 收敛） | 不满足一律不删（9.2 行为 + 缓冲上浮） |
| 账本镜像 | 站点 history 观察名单（`history?hnr=1`，1~3 请求/轮、1rps 节流、30 分钟缓存） | **服务器权威**：名单中的种子（观察中/已记账）一票否决豁免，本地时长达标也不放行 |
| 标定 | 账本服务器做种时长 vs 客户端统计的漂移 | 缓冲从 6h 起步按 EWMA 收敛为实测值 |

- 新记账命中按任务通知开关提醒，并说明自愈语义（继续做种到倒计时归零自动解除；
  BP 清除按 10 BP/小时计价，仅建议用于死种或紧急占坑）；
- 策略详情的 H&R 列表展示服务器侧剩余时长、观察/记账状态与 BP 标价；
- 账本同步失败静默降级，基线闸门（公式 + 缓冲）继续兜底，只多保不早放。

## 做种窗口与红区（9.4 新增）

ExoticaZ 的 H&R 要求时长必须在**下载完成后 96 小时内**达成（锚点 = 完成时刻，
离线消耗窗口但不计做种时长；窗口到期未达标，做种中也记账）。9.4 据此补齐：

- **删除提交前强制 re-announce**：服务器做种时长只在 announce 入账（两次 announce
  之间倒计时冻结），删除前触发一次汇报让服务器尽快结算（失败不阻断，基线闸门已保守）；
- **红区判定**：剩余窗口 < 剩余要求 + 缓冲 → 策略详情显示红色"红区·窗口紧迫"徽章，
  提示禁止长时间离线；红区种子本来就受 H&R 硬保护，不会删种；
- **站点策略新增窗口属性**（`SiteHRRule.window_hours`，ExoticaZ=96h），随站点规则配置；
- **标定缓冲收敛下限 0.75h**（1.5×announce 周期）：漂移样本偏小时缓冲不被拖穿。

## 发布时间窗口对相对时长站点的兜底（9.4 新增）

MP v3.0.10-1 的定义过滤器集合不含 `date_en_elapsed_parse`（未匹配即静默空操作），
相对时长站点（如 ExoticaZ）的 pubdate 会缺失。9.4 起发布时间窗口过滤在 pubdate
不可用时自动回退解析定义 `date_elapsed` 字段的原始相对时长文本
（"20 minutes"/"1 hour 30 minutes"/"3 days"），窗口过滤不退化。

适配与对拍细节（新站点接入步骤、31 条规范向量、请求纪律）见
[sites/README.md](./sites/README.md)；规则权威语义以
MoviePilot-Resources 参考包的《MPV3-适配设计与交叉验证说明》为准。

旧条件删种、动态删种、全局删种托管、模拟删种和 7.3 兼容引擎在 9.1 中不再注册或执行。手动清理必须先经过 5 分钟只读预览、配置版本校验和执行前二次安全复核；升级前任务配置保存在不可覆盖的 `v9_task_config_backups` 中。

## 界面

- 首页：响应式任务健康卡、容量、每日上传、异常数量和下一步。
- 任务详情：状态、种子、记录三个入口；策略分数、学习样本和保护原因位于“策略详情”。
- 配置：站点与任务、空间与速度、选种方式、删种与安全四步向导，并在保存前生成白话预览。
- 工具与设置：插件开关、全局硬上限和独立站点签到；签到不参与刷流决策。

## 迁移

- 数据版本为 9，迁移可重复执行，不覆盖首次保存的升级前备份。
- 保留站点、下载器、目录、标签、调度、分享率目标、容量、带宽、促销、H&R、大小、发布时间、文本筛选、最低保种、排除标签和删除数据选择。
- 旧单值大小解释为最小体积；范围拆为明确最小值和最大值。
- 曾启用智能、动态或条件删种的任务统一迁移到均衡策略并进入 48 小时观察；未设置容量或最低保种时自动暂停删种并提示完善。
- 原来关闭删种的任务保持关闭；种子身份、上传历史、学习数据和审计继续保留。

## API

基础路径为 `/api/v1/plugin/BrushFlow`，均使用宿主 Bearer 认证。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/status` | 全局状态、任务健康摘要与可选站点下载器 |
| `POST` | `/settings` | 插件、全局硬上限与签到设置 |
| `POST` | `/tasks` | 创建 9.1 嵌套任务 |
| `GET / PUT / DELETE` | `/tasks/{task_id}` | 查询、按 revision 更新或删除任务 |
| `GET` | `/tasks/{task_id}/torrents` | 分页获取任务种子 |
| `GET` | `/tasks/{task_id}/events` | 分页获取运行记录 |
| `POST` | `/tasks/{task_id}/cleanup/preview` | 只读预览本轮清理名单 |
| `POST` | `/tasks/{task_id}/actions/{action}` | 统一任务操作入口 |
| `POST` | `/signin/run` | 立即执行站点签到 |

统一动作包括 `run_selection`、`run_check`、`pause_task`、`resume_task`、`activate_deletion`、`extend_observation`、`pause_deletion`、`resume_deletion`、`retry_stalled` 和 `pause_stalled`。

## 构建

在本目录执行 `pnpm build`。构建会先验证 Python、插件 `package.json` 与根目录 `package.v3.json` 的发布版本一致性，再验证前端默认值并生成 `dist/assets`。
